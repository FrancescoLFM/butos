# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Butos is a 32-bit x86 bare-metal kernel (GNU as + freestanding C99) booted from a raw disk image in QEMU. Goal: a framework for running other bare-metal programs; it can already load and run an ELF from a FAT32 partition. Comments, makefile messages and `TODO.md` are partly in Italian.

## Build / run

Builds on Linux and macOS. `toolchain.mk` (included by every makefile) picks the compiler: native `gcc -m32` on Linux, `i686-elf-` cross toolchain on macOS (`brew install i686-elf-gcc dosfstools mtools qemu gdb`); override with `make CROSS=<prefix>`. Use `$(CC)/$(AS)/$(LD)/$(OBJCOPY)/$(STRIP)` and `$(MAKE)` in makefiles, never bare tool names, and stick to POSIX shell in recipes (no `echo -e`, GNU `stat`, `sed -i` without suffix). The FAT32 partition is populated with mtools (`mcopy`), no mounting/sudo.

- `make` — full build: boot stage 2 → kernel → real-mode bootloader/MBR → disk image `qemu/vhdd.img` → FAT32 partition (`mkfs.fat`) with `programs/bin/*` copied in via `mcopy`.
- `make run` / `make vnc` — boot the image in `qemu-system-x86_64` (PIIX3 IDE disk, 2G RAM).
- `make debug` — QEMU with `-s -S` plus gdb using `src/butos` symbols and `scripts/butos.gdb` (breaks at `main`). Build without optimizations for usable debugging.
- `make disass` — objdump of the kernel ELF.
- `make clean`.
- Sub-builds: `make -C src`, `make -C src/boot`, `make -C init`, `make -C programs`.

All C is compiled with `-Wall -Wextra -Werror -m32 -ffreestanding -nostdlib -mgeneral-regs-only -std=c99`; warnings break the build. `-mgeneral-regs-only` means no floating point/SSE in kernel code. Includes are rooted at `src/` (`#include <libs/print.h>`, `<cpu/idt.h>`, ...).

There is no test framework. `src/test.c` contains ad-hoc in-kernel test functions (`test_ata_io`, filesystem tests, `syscall_test`, `elf_test`, ...); `src/main.c` calls one of them after init. To "run a test", change which function `main()` calls, rebuild and `make run`.

## Boot chain and disk layout

Pieces are stitched together with `dd` in the top-level `makefile` — offsets there must stay consistent with constants in the assembly:

1. `init/mbr/mbr.s` (sector 0, linked at 0x0600) — self-relocates, loads sector 1 to 0x7C00.
2. `init/init.s` + `init/libs/*.s` (sector 1, 0x7C00) — real mode: reads stage 2 (`bootloader_start` 0x7E00, `bootloader_size` sectors) and the kernel (to `kernel_start` 0xF000), loads GDT, enters protected mode, copies the kernel to 0x100000, jumps to stage 2. Kernel sector count `SEC` is computed at build time from `src/butos.bin` size (`init/makefile`), so `src` must be built before `init`. Addresses live in `init/include/macro.s`.
3. `src/boot/startk.c` (image sector 2, linked at 0x7E00) — `paging_init()` (identity map + higher-half map), moves the stack to 0xC00F0000, jumps to 0xC0000000. Built separately but reuses `src/cpu/paging.c` and `apaging.s`.
4. Kernel `src/` (image sector 66, physical 0x100000, linked at virtual 0xC0000000 via `src/butos.ld`, entry `main`).
5. FAT32 partition image written at sector 203 of `qemu/vhdd.img`; holds user programs.

Changing stage-2 size or these sector offsets requires updating both the `makefile` `dd seek=` values and `macro.s`. The build fails if the kernel outgrows the 137 sectors before the FAT partition. Page directory entries default to not-present, so stray accesses page fault instead of silently hitting physical page 0.

## Kernel architecture (`src/`)

- `main.c` init order: zero `.bss` (the bootloader doesn't) → `page_directory_adjust()` → `isr_install()` (IDT, PIC, ISRs) → VGA → `kalloc_start()` with a hard-coded heap at 0xC00F0000 → keyboard → test function.
- `cpu/`: IDT/ISR (`idt.c`, `isr.s`), PIC, paging (`paging.c` + `apaging.s`, also linked into stage 2, so no kernel heap there), `vmm.c` (kernel-only: map ranges into a page directory with heap-allocated page tables), processes (`proc.c`: `process_exec(elf, &exit_code)` maps the whole image as one contiguous physical block in a per-process page directory, loads segments, calls the entry in ring 0 on the kernel stack, restores the kernel CR3 and frees everything — no ring 3/scheduler yet).
- `drivers/`: VGA text mode, PS/2 keyboard (layout tables generated by `scripts/keyboard/keyboard_gen.py` from `keyboard.json`), PCI enumeration, ATA PIO.
- `fs/`: `disk.c` is an abstract disk over the ATA driver (with MBR partition offset lookup); `fat32/` implements FAT32 (table, cache, dir, file); `elf.c` parses ELF32 and loads program headers. Functions return status enums (`disk_status`, `elf_status_t`, ...) — follow that error-handling style.
- `libs/`: `alloc.c` (kernel heap `kalloc/kfree/...` on top of the generic region allocator in `allocator.c`), printk/puts, scan/gets, string, queue, shell, syscalls.

## Syscalls / user programs

- `int 0x80`, syscall number in EAX, args in EBX/ECX. Dispatch: `isr.s` → `syscall_handler` in `cpu/idt.c` → `syscall_handlers[]` table in `src/libs/syscalls.h`.
- User-side wrappers are duplicated in `programs/include/syscalls.h` (and also in `src/libs/syscalls.h` for kernel-side testing). Adding a syscall means: handler in `src/libs/syscalls.c`, entry + bump `SYSCALLS_NUM` in `src/libs/syscalls.h`, and the wrapper in both headers.
- Programs live in `programs/sources/<name>/` with their own makefile and linker script (example links at 0x01000000, entry `main`), output to `programs/bin/`, and are copied onto the FAT32 partition by `make`. The kernel loads them by path (e.g. `/example`).
